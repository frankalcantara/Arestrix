# How Arestrix memory works

> **Applies to:** Arestrix 2.6 — last reviewed: 2026-11-02
>
> A one-page guide and reference for project memory. Memory is optional, local and owned by the
> project. There is no automatic import of old formats.

## 1. Principles

- **Off by default.** No vertex reads or writes knowledge without explicit configuration.
- **Three modes.** `off`, `consult` and `learn`, decided per vertex.
- **Learning implies saving.** `learn` writes an episode and may propose knowledge; `consult` only reads.
- **Derived knowledge requires a gate.** Lessons, facts/claims and playbooks go through
  proposals/candidates and validation; paths only activate with validated distinct inputs. Sources
  and passages are ingested and become active after the run; bridges remain hypotheses and never
  become automatic edges.
- **Telemetry is separate.** Episodes, hits and API usage live in their own database. Clearing a
  session or pruning telemetry never deletes knowledge.
- **Local-first.** SQLite on the project disk; no cloud dependency.

The cycle is:

```text
consult → execute → observe → propose → approve → consolidate → consult
```

## 2. Where memory lives

| Scope | Path | Role |
| :--- | :--- | :--- |
| Project knowledge | `<project>/.arestrix/memory/memory.db` | lessons, facts, evidence and working state |
| Project telemetry | `<project>/.arestrix/telemetry/telemetry.db` | episodes, hits, token usage and validations |
| Workspace | `<project>/.workspace/memory/memory.db` | promoted, shared knowledge |
| Institution | institution service database | authenticated cross-project knowledge |

`ARESTRIX_MEMORY_DB` overrides the knowledge database and `ARESTRIX_TELEMETRY_DB` overrides
telemetry. The project root comes from `ARESTRIX_PROJECT_ROOT`.

## 3. Vertex configuration

| Field | Effect |
| :--- | :--- |
| `mode: off` | Reads and writes no memory. |
| `mode: consult` | Injects the authorized brief into the prompt. Writes no knowledge. |
| `mode: learn` | Consults, then writes an episode and lesson proposals at the end. |
| `theme` | Main read/write theme. Without it: legacy `domains[0]`, then active skill name, label and vertex id. |
| `readThemes` | Extra read-only themes. |
| `taskType` | Stable continuity identity; defaults to the vertex id. |
| `contextBudgetTokens` | Brief budget; `0` disables injection. |
| `contextCompaction` | Off by default. Compacts finished turns into a derived block with `[MEMO:<id>]` references using existing memory; failures keep the original history. |
| `catalog.mode` | `off`, `warn` (default) or `strict`. The v1 catalog defines predicates, cardinality, context keys and units; in `strict`, an unknown/structural predicate or missing required context becomes an `unresolved` proposal. |
| `catalog.path` | Project catalog, default `.arestrix/memory/catalog.json`. A project cannot change built-in cardinality without an audited `override`. |
| `maxLessonsPerRun` | Proposal limit per run. |
| `maxLessonChars` | Character limit per lesson/trigger. |

Project settings provide the inherited default: mode, theme, retention, consolidation and
embeddings. A vertex may override memory when `inheritMemory` is false.

The **effective theme** follows the same order in TypeScript and C++: explicit `theme`; legacy
`domains[0]`; active skill name; vertex label; vertex id. The last three become identifiers
(lowercase, accents folded, `_` separators). The vertex window shows the theme and its origin
(“from skill”, “from label” or “from id”). Changing the active skill without an explicit `theme`
**changes the theme and therefore the lesson filter and write authorization**; declare the theme
to keep it stable.

## 4. What the brief contains

The brief is built at the start of the run, within the configured budget. The query combines the
`task_type`, the theme and the vertex's **prompt template** — never user input text. Lessons are
filtered by theme directly in SQL, without scanning every project lesson, and the brief is cached
per vertex/run; any knowledge write, promotion, consolidation or reindex invalidates the cache.

1. **Active lessons** for the theme, ordered by confidence and recency.
2. **Active facts** linked to the theme and task queries.
3. **Eligible active paths** when `memory.pathServing` is enabled; every claim must be active, in
   validity and allowed by the access policy.
4. **Traversal pack** when no path covers the query and `memory.traversal` is enabled.
5. **Evidence** for the injected lessons and facts.
6. **Working state** only when the legacy/manual format enables it. Graphs generated by Arestrix
   do not use this block.

Compiled playbooks remain **candidates** and do not enter the brief until promoted. Knowledge with
low confidence, an open conflict or expired validity is not injected.

With `globalDefaults.memory.promptCache` enabled, the **skill + brief** prefix is sent to the
Anthropic provider as a system block with `cache_control: ephemeral`; the execution context stays in
a second, uncached block. The order skill, brief and context is fixed and the brief is identical
across turns of the same run, so providers with automatic prefix caching (OpenAI-compatible) also
benefit from the resend. `memory report` shows the fraction of input tokens served by the cache.
The switch is off by default.

Every injected item is labeled `[MEMO:<id>]`. At the end of the run, the runtime marks an item as
**used** only when the agent cites its ID in the final answer. “Injected”, “consulted” and “used”
are distinct signals: `memory_search` results also carry `[MEMO:<id>]` and the same citation
instruction, but returning them only marks `consulted`. Citing an ID that was not delivered in
that run is ignored and counted as an invalid citation.

Use changes an item's **utility**, not its confidence. Confidence is sustainment (evidence,
validation and promotion); utility is the usage history across successful and failed runs.

## 5. How learning enters

A `learn` run writes an **episode** with input, result, validation and hashes. From it, the system
may create:

- a **lesson proposal** (`memory_propose_lesson`) when the agent states a rule;
- an **automatic failure proposal** when the task fails (validator rejection or `maxTurns`);
- a **playbook candidate** when there is enough evidence of a successful sequence.

Infrastructure failures are classified by an enumerated `errorClass` — transport/timeout, 429,
5xx, auth/key, gateway/budget, configuration, sandbox/tool or cancellation — and do **not** create
a lesson proposal. The agent throws `AgentFailure` with that class; the generated wrapper checks the
class, never the exception text. `task_max_turns` is a task failure, not infrastructure. The
proposal text is normalized before deduplication: UUIDs, timestamps and long numbers become
placeholders, so two identical failures with different IDs produce a single proposal.

### Artifact validation

When a vertex declares `validationRules` — a path with `{itemId}`, a minimum size and a content
pattern — the runtime evaluates the rules **after** the agent finishes without an exception. The
verdict is stored in `memory_validation`, linked to the vertex episode, with
`validator_id=artifact-rules`, the SHA-256 of the canonical rules and the hash of the artifacts
read. Infrastructure or task failures produce no verdict: the episode stays **without a verdict**.

With `globalDefaults.memory.validatedReinforcement` enabled, the agent result no longer changes
utility; only the verdict reinforces the items used in that run. Disabled (the default), the 2.5.0
behavior is preserved. The playbook gate always uses the verdict, with or without the switch.

Proposals stay pending in the **Project Memory** panel. Approval promotes the item to active
knowledge; rejection keeps the record for audit. There is no direct lesson-writing tool.

Every promotion and demotion writes an **evidence snapshot** to `memory_evidence` in the
knowledge database: target, action, source episode (when available), validator, artifact hash,
summary and excerpt hash. The snapshot has **no foreign key to the episode**, so telemetry
retention can delete old episodes, hits and validations without deleting the proof. The report and
the panel show how many snapshots exist and how many active items lack evidence.

Playbooks leave `candidate` only with independent validation. The gate requires **3 distinct
`input_hash` values** among the last 20 validated runs for the same `task_type`, a stable validator
and at most **1 promotion per `task_type` in 24h**. Two consecutive failures or more than 30%
failures in 10 validated runs return the playbook to candidate. In the panel, an active playbook has
a **Back to candidate** button; the CLI equivalent is `memory unpromote`. Manual approval of a
playbook proposal is an explicit operator exception and does not pass through the automatic gate.

Facts also have **predicate cardinality**. Accumulation predicates — `USES`, `USES_TOOL`,
`PRODUCES`, `READS`, `WRITES`, `TOUCHES`, `CITES`, `INCLUDES`, `TAGGED_WITH`, `HAS`, `DEPENDS_ON` —
accept multiple active objects. Functional and unknown predicates are single-valued: promoting a
new value ends the previous one (`superseded`, with history) instead of leaving two active values.
The contradiction detector ignores multi-valued predicates.

## 6. Agent tools

| Tool | Effect |
| :--- | :--- |
| `memory_search` | Read-only project/workspace search; accepts `mode: graph` for traversal when enabled. |
| `memory_propose_lesson` | Records a pending lesson proposal; does not activate knowledge. |
| `memory_state_get` | Reads a declared state key; the value is labeled untrusted. |
| `memory_state_set` | Writes with CAS (`expected_version`); `learn` mode only. |
| `memory_state_list` | Lists visible keys and metadata, without values. |
| `memory_state_history` | Lists versions of a `versioned` key. |

`memory_record_lesson`, `memoryWriteKeys` and the native `arestrix.memoria` server were removed.
Knowledge is accessed by the runtime and the panel, not by a parallel key-value store.

## 7. Search and embeddings

Search combines:

- **lexical** (FTS), always available;
- optional **vector** search when an embedding provider is configured;
- **RRF fusion** to rank both result sets.

Search **does not index** during a query. Indexing happens outside the read path: at the end of
every persistent run (default budget of **10 s or 64 objects**), in the maintenance worker
(`idle`/`after_episodes`) and in the panel's explicit **Test** and **Reindex** actions. An embedding
provider failure never fails the run. Ready profiles:

| Profile | Stored dimensions | Note |
| :--- | :--- | :--- |
| EmbeddingGemma 2 | 768 | full vector; also accepts 512, 256 and 128 via MRL |
| Qwen3-Embedding-4B | 768 | truncated from 2560; accepts 32 to 2560 via MRL |

Without a provider, search keeps working in lexical mode.

Each model has its own representation prefix. **Qwen3** receives the query instruction
`Instruct: Given a task description, retrieve memory items that help complete it` followed by
`Query:`; the document gets no prefix. **EmbeddingGemma 2** uses distinct query and document
prefixes. The instruction text is versioned and part of the **fingerprint**: changing it
invalidates the index.

The **model revision** field (`embeddingRevision`) records the server digest/revision when
provided; it is also part of the fingerprint. **MRL truncation** (`embeddingTruncateDim`, 0 = full)
reduces the vector and **renormalizes it to norm 1**; NaN/Inf or zero-norm vectors are rejected.
Accepted dimensions: EmbeddingGemma 2 at 768, 512, 256 or 128; Qwen3 from 32 to 2560.

The index stores a SHA-256 **fingerprint** of the endpoint, model, revision, effective dimension,
truncation, prefixes/instruction, normalization, metric and index version. Search only uses vectors
from the current fingerprint and never mixes old indexes. Changing the model, revision, dimension,
truncation or instruction leaves the index `stale` and requires reindexing. Status shows the model,
dimensions, revision, indexed items, candidates, pending items and a short fingerprint, with these
states:

| State | Meaning | Search |
| :--- | :--- | :--- |
| `ready` | Current fingerprint, complete index | hybrid |
| `stale` | Model/dimension/endpoint/template changed | lexical |
| `pending` | Reindex in progress | lexical |
| `partial` | Incomplete index | hybrid: vector for indexed items, lexical for the rest |
| `failed` | Reindex failed | lexical + error |

In `partial`, items with a vector enter the lexical + vector fusion; items still without a vector
enter only through the lexical side, without turning hybrid search off. `memory health` and the
panel show indexed and pending totals.

Changing profiles invalidates the index and offers reindexing. Reindexing is idempotent and
discards vectors from old fingerprints.

## 8. A/B measurement

The panel offers **Preview brief size**. The action:

1. creates a consistent copy of knowledge with `VACUUM INTO`;
2. computes the SHA-256 fingerprint of the copy;
3. measures, per active vertex, brief tokens and characters, lessons, facts and playbooks;
4. compares with the no-memory baseline (zero).

This is **A/B v1**: it measures context cost and content, not the validator approval rate. The full
executor is the `memory ab run` command described below.

**A/B v2** is the full statistical protocol. The versioned suite
[`tests/fixtures/memory-ab-v1.json`](../../tests/fixtures/memory-ab-v1.json) has 20 tasks — 12 with
relevant knowledge, 4 controls and 4 known failures — and each declares its `input_hash`. The CLI
validates the suite, shuffles an interleaved order with a seed and analyzes observations:

```bash
arestrix-cli memory ab validate --suite tests/fixtures/memory-ab-v1.json
arestrix-cli memory ab order --suite tests/fixtures/memory-ab-v1.json \
  --repetitions 3 --seed 42 --json
arestrix-cli memory ab run --suite tests/fixtures/memory-ab-v1.json \
  --pipeline pipeline.json --node gerador --repetitions 3 --seed 42 --json
```

`memory ab run` actually executes the pilot. It freezes knowledge with `VACUUM INTO` and opens that
copy read-only (`SQLITE_OPEN_READONLY` and `PRAGMA query_only`) in the ON arm; the OFF arm sets
`ARESTRIX_MEMORY_DISABLE=1`. Both halves write telemetry to the same measurement database, with
`ab_arm` and `ab_repetition` on every row. Infrastructure failures are retried up to twice and
counted outside the verdict; tasks without a validator appear in `invalidTasks` and do not enter the
pair.

The primary metric is **validator approval**, compared in pairs. The report includes paired deltas,
95% CI (Student t), tokens, turns and latency, plus the knowledge fingerprint before and after the
measurement. Monetary cost is not computed in this version. `memory ab report` remains available for analysing an observation file collected
elsewhere.

### Recurrence milestone

E10 measures whether tasks repeat often enough to justify paths. The episode
records `intent_template_hash`, the SHA-256 of the vertex `promptTemplate`
before variable substitution. The template is configuration, not the user
prompt, so this field never stores input text.

```bash
arestrix-cli memory report --recurrence --json
arestrix-cli memory report --recurrence --since 2026-10-01T00:00:00Z \
  --min-verdict-rate 0.70 --min-citation-rate 0.30 \
  --min-executions 5 --min-distinct-inputs 3 --min-reuse-rate 0.20
```

For each `task_type`, the report includes executions, executions with a verdict,
approval rate, distinct `input_hash` values, (`task_type`,
`intent_template_hash`) pairs, citation rate, reuse rate and tokens per
execution. Reuse is the fraction of executions that cite an item already cited
by an earlier execution of the same `task_type`. The result selects one of
`continue_full`, `continue_base_knowledge` (E11-E14),
`fix_validators` or `insufficient_data`. The thresholds used are stored in the
JSON.

### Local sources and passages

With `globalDefaults.memory.sources` enabled, memory ingests text, Markdown and
code files **after** execution, without calling a language model:

- files successfully read by the `read` tool;
- folders or files declared in `memory.sources.paths`.

Ingestion applies an extension allowlist, `maxFileBytes` (default 512 KiB),
`maxFiles` (default 2,000) per run, fixed exclusions (`.git`, `node_modules`, `.arestrix`,
`.workspace/memory`) and secret sanitization. Content is segmented
deterministically: Markdown by headings/paragraphs, code by top-level blocks and
text in 1,000-character windows with 200 characters of overlap.

Each source version has a `content_hash`; changes create a new version and old
passages become `superseded`, preserved as evidence. Re-ingesting identical
content is a no-op. `memory_search` returns passages with `[MEMO:psg:<id>]`,
path and position; citing the ID marks the passage as used. The brief does not
include passages at this stage.

### Claims from passages

With `globalDefaults.memory.claimExtraction` enabled, maintenance selects
passages with `used=1` in approved executions that have not been extracted by
the current extractor fingerprint. The **Studio local agent** is the only
intelligence layer: memory sends it the passage, the catalog summary and the
output contract, and receives JSON back. Memory does not configure provider,
protocol, URL, key or model; the local agent never runs during agent execution.

A project can choose the intelligence target with
`memory.claimExtraction.agent`: a Studio agent id, or an object with `id`,
`graph` and `node` for a graph-backed agent. When the field is absent, the
Studio default model is used (today, DeepSeek Flash 4.1 1017 in this
installation). When it is present but the agent is not registered, extraction
fails explicitly instead of silently falling back to another model.

Each claim becomes a pending `claim` proposal with subject, predicate, object or
value, unit, polarity, qualifiers, validity, lens and `quote`. Validation
requires valid JSON, a quote literally present in the passage, parsable dates and
unit, and alias entity resolution; an ambiguous mention abstains. Predicates
outside the catalog remain as flagged proposals.

Promotion is manual and writes an edge with lens, citation and extractor
fingerprint in metadata, plus an evidence snapshot. For single-valued predicates,
only values with overlapping validity close the previous one; disjoint intervals
remain as history.

### Forgetting a source version

Schema v7 adds `memory_lineage`, `memory_tombstone`, `memory_job` and
`memory_removal_log`. `memory forget` resolves one source version or all
versions of a URI, walks the lineage from its passages and removes the closed
derivation set in one `WriteTxn`: claims supported only by the erased source are
retracted with `retracted_at` and `status='rejected'`, proposals and derived
objects are tombstoned, evidence and passages are deleted, and the removal log
gets one row per item. The source URI receives a tombstone, so automatic
ingestion is blocked until an explicit `--allow-forgotten` path is implemented.

Telemetry is cleaned by the idempotent `purge_telemetry` job. The job never
receives the erased text; it receives 64-byte rolling-window hashes and redacts
episodes that contain a literal copy. The first cut finds copies of 96 bytes or
more and deliberately does not claim to find paraphrases. Without `--async`,
`forget` drains the job before returning and reports a distinct pending state
when the telemetry database is unavailable.

### Prefix epochs and removals during a run

Schema v8 adds `memory_prefix_epoch`. The stable block contains only active
lessons and playbooks, sorted by `(kind, id)` and formatted deterministically, so
utility, traversal scores and working state cannot change its bytes. With
`memory.prefixEpochs` enabled, the stable block is built from the latest
published epoch; additions made after that epoch stay in the dynamic block until
the next publication. The
`MemoryBriefInfo` carries the stable block, prefix key/identity/epoch and
`removalSeqStart`; `briefInfoToJson` is the contract consumed by generated
pipelines. With lenses enabled, active facets are delivered as volatile lines
with their `facetIds`; served paths keep their `pathIds` and claim ids.

Before every model request, the agent calls `MemoryService::removedSince` with
the delivered `(kind, id)` set. A matching removal rebuilds the prompt without
the item and removes the whole memory line carrying its `[MEMO:<id>]` marker
from the system prompt and tool history; a `scope` removal clears the delivered
set. A removal that changes the published stable set also publishes a new epoch
immediately. The check stays enabled even when epoch
publication is disabled, so a committed removal cannot be served again. The
epoch table records the published item set; provider and model remain trace
data, not prefix identity. `memory.prefixEpochs` accepts `enabled`,
`cacheTtlSeconds`, `maxPending` and `minIntervalSeconds`; generated agents
publish when the idle TTL expires or when the pending-addition threshold is
reached after the minimum interval. Removals publish immediately. A skill or
template change produces a new `prefix_identity` in the trace without advancing
the epoch when the published content hash is unchanged; the prefix step records
the identity, epoch and `delivered_ids_source`.

### Lenses and facets

With `globalDefaults.memory.lenses` enabled, maintenance ensures a lens for every
active edge (the lens comes from extraction or the writer's theme/domain) and
builds deterministic facets per entity and lens. Facets include only active
claims; proposed or contested claims are excluded. When `claims_hash` changes,
the facet is updated with a new revision; reprocessing the same set leaves the
revision unchanged.

Facets use the **symmetric** embedding role, with its own prefix (EmbeddingGemma:
`task: sentence similarity`; Qwen3: similarity instruction) and a fingerprint
distinct from retrieval. `memory_search` derives the lens filter internally from the
vertex themes and returns only edges belonging to that lens.

### Canonical paths

With `globalDefaults.memory.paths` enabled, maintenance consolidates approved
traces into canonical claim paths. Consolidation is idempotent by `trace_id`:
reprocessing the same trace leaves statistics unchanged. A path starts as
`candidate` and only becomes `active` after a configurable number of distinct
inputs (`minDistinctInputs`, default 3).

Utility uses the Beta mean with a prior (`(successes + prior) / (successes +
failures + 2·prior)`) and optional time decay (`mu`). The prior prevents a single
success from reaching 1.0; out-of-order traces never produce negative decay.
The telemetry credit ledger records each validator verdict as a `citation`
event split across the distinct cited items, or as `presence_low_res` across the
delivered items when nothing was cited. Events are idempotent and update
`memory_item_utility` in the same transaction; the item key resolves edges
through `claim_key`. With `memory.utility.source='ledger'`, hybrid and
lexical-only recall multiply each candidate score by its ledger utility; `edge`
is the default and keeps the previous ranking. Legacy edge/playbook counters are imported once as
`legacy_seed`, and the aggregate can be rebuilt from events with
`memory utility status|seed|rebuild`. Credit per origin and item/class is capped
inside `originWindowDays`; excess events keep a zero delta with `capped=1`.
If a telemetry write fails, credit events are appended to
`credit-outbox.jsonl` and drained on the next validation.

When a rejected task has an ablation audit, the observed baseline, no-memory
and one-item-removed arms decide the outcome. An item is decisive when removing
it flips the verdict in the majority of repetitions; the failure is then
reversed from the cited items and assigned to the decisive one. Infrastructure
failures and unstable repetitions keep the audit inconclusive. Reviews of
validator approvals are stored in telemetry, and the estimated divergence uses
a 95% Wilson interval; `memory.creditAudit.enabled` keeps the current automatic
promotion until the configured minimum number of reviews is reached. Task
snapshots are also telemetry-only and are rejected above `maxSnapshotBytes`.
`memory audit-credit [--status S] [--report]` lists audits, and
`memory validator-audit [record] --validator V --trace T --verdict
accepted|rejected` records or summarizes reviewer verdicts.

The sampler walks recent rejected validations, counts delivered-but-uncited
items as suspects, and selects a task when it has a suspect or when its stable
hash falls below `sampleRate`. It records `no_snapshot`, `snapshot_expired`,
`package_in_input`, `external_effects` and `validator_suspended` instead of
auditing those tasks, and stops when `maxAuditsPerDay` or `maxTokensPerDay` is
reached. The actual arms are produced by the registered
`CreditAuditExecutorFn`; the memory module never talks to a provider or
sandbox directly. `memory audit-credit --run` executes the sampler and
`--dry-run` only lists the selected candidates. With audit enabled, each agent
node writes its pre-brief input to `memory_task_snapshot` at the end of the run;
episodes that used MCP or `call_agent` are marked `external_effects`.

#### Audit container contract

Every arm of an ablation audit gets its own ephemeral Docker container and its
own workspace. Nothing is shared between arms: a file written by one arm is not
visible to another, and all outputs are discarded after the verdict.

| Control | Value |
| --- | --- |
| Image | `debian:stable-slim` by default; `ARESTRIX_SANDBOX_IMAGE` or `memory.creditAudit.containerImage` overrides it. |
| Runtime | `docker run --rm --init`; one container per arm and repetition. |
| Filesystem | Root filesystem read-only, `/tmp` mounted as `tmpfs`, workspace mounted read-write at `/workspace`. |
| Workspace source | A copy of the task snapshot, or a git worktree with the saved patch applied. The memory and telemetry databases are never mounted. |
| Network | `--network=none`. Model calls happen in the host process, never inside the container. |
| Privileges | `--cap-drop=ALL`, `--security-opt=no-new-privileges`, user `1000:1000`, no host fallback. |
| Limits | `containerMemoryMB` (default 512), `containerPidsLimit` (default 256) and `containerTimeoutSeconds` (default 300). |
| Tools | `read`, `write`, `edit`, `validate_svg`, `retrieve` and `bash` (inside the container). |
| Disabled | `memory_search`, memory write/state tools, `call_agent`, MCP servers and interaction nodes. |
| Secrets | No provider keys, tokens or user environment variables are injected. |
| Budget | `maxAuditsPerDay`, `maxTokensPerDay` and, when configured, the `memory-audit` gateway budget. |

`creditAuditContainerPlan()` returns this contract to the registered
`CreditAuditExecutorFn`. If no container driver is available, the task is not
auditable instead of silently falling back to the host.

When a dependent claim is retracted, expires or stops being active, the path is
suspended in the same maintenance pass. If all dependencies become valid again,
it is reactivated; otherwise it can be retired.

```bash
arestrix-cli memory paths list --project . --json
arestrix-cli memory paths show <path> --project . --json
arestrix-cli memory paths retire <path> --project .
```

### Path serving

With `globalDefaults.memory.pathServing` enabled, the brief and
`memory_search` try active paths compatible with the `task_type` first. Every
claim must be active, in validity and allowed by the access policy; if one
fails, the whole path is not served. The path appears as
`[MEMO:path:<id>]` with its claims and sources. Citing the path counts as using
its claims; citing a claim also marks the path. A configurable fraction of
queries uses Thompson sampling and is recorded in the trace.

Paths with enough utility and uses materialize derived `via_caminho` edges.
They are reconstructible projections, not evidence, and are excluded from
conflict detection and normal search; they follow the path state. The switch
stays off until the A/B result is recorded.

### Beam traversal

When no path covers the query, `globalDefaults.memory.traversal` enables a
bounded traversal from anchors resolved by alias, FTS and optional vector
candidates. The search limits beam width, depth, expanded candidates, time and
characters; ineligible items never enter the top-k and cycles do not repeat
nodes. `memory_search` accepts `mode: "graph"` for this route.

The pack returns each item with source, validity and justification, and records
the coverage vector in the trace: best path utility, sustained fraction,
conflicts, intent distance and abstention. Traversal only reads the graph and
never writes knowledge.

### Interdomain bridges

With `globalDefaults.memory.bridges` enabled, maintenance looks for the same
entity across distinct lenses in approved traces and records a
`bridge_hypothesis` **hypothesis** with conditions, candidate claims and paths.
Detection is budgeted per run, limited per entity and deduplicated by lens pair;
discarded events appear in the report and in `memory bridges detect`. No edge is
created automatically: promotion is manual, as for any proposal.

### Model routing

The router estimates local-tier confidence from validation outcomes per
`task_type` with a Beta prior. In `routing.mode=binary` it chooses between local
and frontier tiers using `p_min` and expected cost; in `shadow` it records the
decision without changing the executed model. `memory.localOnly` blocks the
remote tier for the whole project. The decision is written to the trace;
automatic escalation after validator failure is not executed by the runtime yet.
The default is `off`.

### Retrieval traces

Every knowledge write bumps `knowledge_version` in the same transaction; reads
and telemetry do not. Usage-only updates (utility, success/failure counters,
`last_used`, path statistics) no longer bump it, while `status` and
`dormant_at` still do. Every memory-enabled vertex execution records a
`memory_trace` with the version consulted, the brief and searches, candidates
with lexical/vector/fused scores, position and delivered status, plus the items
actually used. The trace closes with the episode and is idempotent by
`(run_id, node_id)`.

```bash
arestrix-cli memory trace show <run> <node> --project . --json
```

Each query stores at most 50 candidates and each execution at most 8 steps; the
overflow is counted in `truncatedCandidates`/`truncatedSteps`. The query itself
is stored as a hash, not as text.

### Cost per run

Telemetry records prompt, output and **prompt cache** tokens: cache reads (`cached_tokens`) and cache
writes (`cache_write_tokens`) when the provider reports them. The panel and
`arestrix-cli memory report` show the totals; effective cost uses the provider's normal, cached and
cache-write prices.

## 8.1 Final evaluation

The reproducible evaluation compares lexical, hybrid fallback, facets +
traversal, paths + serving and routing in `shadow`, always over the same frozen
knowledge and budget. The report records tokens, calls, brief, hits and
fingerprints. No experimental switch becomes enabled by default: `pathServing`,
`traversal`, `routing.mode` and `bridges` remain `off` until a real-data
measurement shows a justified gain and cost.

## 8.2 Real-provider validation

Two controlled tests use the real DeepSeek API outside the normal CI, with
`DEEPSEEK_API_KEY`, a token ceiling and a reproducible report. Both ask the same
question and require the same correct answer.

**Long interaction** (`scripts/e2e_memory_deepseek_long.py`): the agent performs
six writes, one search and a final answer. With memory ON it uses the brief and
`memory_search`; without memory it has neither. ON answered `ORION-42` in 9 calls
and 14,164 tokens; OFF answered `UNKNOWN` in 8 calls and 8,475 tokens. The script
now also runs a `compacted` arm with `memory.contextCompaction` enabled: it
answered `ORION-42`, used 12,884 prompt tokens against 13,780 in the ON arm
(**6.5% fewer**), kept the same memory citation (`deepseek-long-lesson`) and
recorded 15 compacted turns in the trace without changing knowledge.

**Context substitution** (`scripts/e2e_memory_prompt_reduction.py`): one arm
receives a long manual in the prompt; the other receives a short prompt and the
same truth from memory. Both answered `ORION-42`. The context arm used 24,718
prompt tokens; the memory arm used 3,228, an 87% reduction.

Memory reduces the **static** context a project must send. Context compaction now
also reduces the **conversation history** of one long run, but the switch remains
off by default until broader real-data measurement. The remaining work is tracked
in [memory-pending.md](memory-pending.md).

## 9. Retention, security and scope

- **Strict scope:** project knowledge does not leak into another project; the workspace is read only
  when configured and authorized.
- **Sanitization:** known secrets are removed before any write, legacy read or export.
- **Retention:** affects telemetry (episodes, hits, usage). Knowledge is not deleted by the retention
  routine.
- **Session clearing:** in ephemeral memory, clears only the session; it never purges a file database.
- **Audit:** approvals, rejections, promotions, conflicts and purges leave a trail.

## 10. Continuation state

Continuation state replaces the old Blackboard and `arestrix.memoria`. It stays **outside the
brief** and is reachable only through tools.

- The key is **declared by the project**; the pipeline agent never creates a key. The Studio
  assistant can only declare one through `memory_declare_state_key`, with human confirmation.
- Identity: `(scope_kind, scope_owner, key)`.
- Scopes: `project`, `task_type` and `item`. Each key has a single scope, with no merge between them.
- The value is validated against a JSON Schema subset **after** secret sanitization.
- `replace` keeps only the current version; `versioned` keeps the last K versions.
- TTL is applied on read.
- CAS: absent `expected_version` creates; equal version writes; a different version returns a
  conflict with the current version and does not overwrite.
- A schema change marks the old value `stale`; the next write provides the current version.
- `memory_state_list` does not return values. Reads are labeled as untrusted data from a previous
  run.
- Successful writes are audited; refusals and conflicts return an error with the current version.
  Detailed refusal auditing is not recorded yet.

In the Studio, the **State** tab in the **Project Memory** panel lists declared keys and lets you
create one with scope, schema, TTL, mode and retained versions. The pipeline agent still cannot
create keys; the Studio assistant can only do so through the confirmed tool.

Declare and operate manually through the CLI:

```bash
arestrix-cli memory state declare --project . --key cursor --scope project \
  --schema '{"type":"object","properties":{"n":{"type":"integer"}},"required":["n"]}'
arestrix-cli memory state set --project . --key cursor --value '{"n":1}'
arestrix-cli memory state get --project . --key cursor --json
arestrix-cli memory state list --project . --json
```
