# How Arestrix memory works

> **Applies to:** Arestrix 2.5 — last reviewed: 2026-10-31
>
> A one-page guide and reference for project memory. Memory is optional, local and owned by the
> project. There is no automatic import of old formats.

## 1. Principles

- **Off by default.** No vertex reads or writes knowledge without explicit configuration.
- **Three modes.** `off`, `consult` and `learn`, decided per vertex.
- **Learning implies saving.** `learn` writes an episode and may propose knowledge; `consult` only reads.
- **Nothing enters on its own.** Lessons and playbooks start as proposals/candidates and become
  active knowledge only after approval.
- **Telemetry is separate.** Episodes, hits and API usage live in their own database. Clearing a
  session or pruning telemetry never deletes knowledge.
- **Local-first.** SQLite on the project disk; no cloud dependency.

The cycle is:

```text
consult → execute → observe → propose → approve → consolidate → consult
```

## 2. Where memory lives

| Scope | Path | Role |
| :--- | :--- | :--- |
| Project knowledge | `<project>/.arestrix/memory/memory.db` | lessons, facts, evidence and working state |
| Project telemetry | `<project>/.arestrix/telemetry/telemetry.db` | episodes, hits, token usage and validations |
| Workspace | `<project>/.workspace/memory/memory.db` | promoted, shared knowledge |
| Institution | institution service database | authenticated cross-project knowledge |

`ARESTRIX_MEMORY_DB` overrides the knowledge database and `ARESTRIX_TELEMETRY_DB` overrides
telemetry. The project root comes from `ARESTRIX_PROJECT_ROOT`.

## 3. Vertex configuration

| Field | Effect |
| :--- | :--- |
| `mode: off` | Reads and writes no memory. |
| `mode: consult` | Injects the authorized brief into the prompt. Writes no knowledge. |
| `mode: learn` | Consults, then writes an episode and lesson proposals at the end. |
| `theme` | Main read/write theme. Without it: legacy `domains[0]`, then active skill name, label and vertex id. |
| `readThemes` | Extra read-only themes. |
| `taskType` | Stable continuity identity; defaults to the vertex id. |
| `contextBudgetTokens` | Brief budget; `0` disables injection. |
| `maxLessonsPerRun` | Proposal limit per run. |
| `maxLessonChars` | Character limit per lesson/trigger. |

Project settings provide the inherited default: mode, theme, retention, consolidation and
embeddings. A vertex may override memory when `inheritMemory` is false.

The **effective theme** follows the same order in TypeScript and C++: explicit `theme`; legacy
`domains[0]`; active skill name; vertex label; vertex id. The last three become identifiers
(lowercase, accents folded, `_` separators). The vertex window shows the theme and its origin
(“from skill”, “from label” or “from id”). Changing the active skill without an explicit `theme`
**changes the theme and therefore the lesson filter and write authorization**; declare the theme
to keep it stable.

## 4. What the brief contains

The brief is built at the start of the run, within the configured budget. The query combines the
`task_type`, the theme and the vertex's **prompt template** — never user input text. Lessons are
filtered by theme directly in SQL, without scanning every project lesson, and the brief is cached
per vertex/run; any knowledge write, promotion, consolidation or reindex invalidates the cache.

1. **Active lessons** for the theme, ordered by confidence and recency.
2. **Active facts** linked to the theme and task queries.
3. **Evidence** for the injected lessons and facts.
4. **Working state** only when the legacy/manual format enables it. Graphs generated by Arestrix
   do not use this block.

Compiled playbooks remain **candidates** and do not enter the brief until promoted. Knowledge with
low confidence, an open conflict or expired validity is not injected.

With `globalDefaults.memory.promptCache` enabled, the **skill + brief** prefix is sent to the
Anthropic provider as a system block with `cache_control: ephemeral`; the execution context stays in
a second, uncached block. The order skill, brief and context is fixed and the brief is identical
across turns of the same run, so providers with automatic prefix caching (OpenAI-compatible) also
benefit from the resend. `memory report` shows the fraction of input tokens served by the cache.
The switch is off by default.

Every injected item is labeled `[MEMO:<id>]`. At the end of the run, the runtime marks an item as
**used** only when the agent cites its ID in the final answer. “Injected”, “consulted” and “used”
are distinct signals: `memory_search` results also carry `[MEMO:<id>]` and the same citation
instruction, but returning them only marks `consulted`. Citing an ID that was not delivered in
that run is ignored and counted as an invalid citation.

Use changes an item's **utility**, not its confidence. Confidence is sustainment (evidence,
validation and promotion); utility is the usage history across successful and failed runs.

## 5. How learning enters

A `learn` run writes an **episode** with input, result, validation and hashes. From it, the system
may create:

- a **lesson proposal** (`memory_propose_lesson`) when the agent states a rule;
- an **automatic failure proposal** when the task fails (validator rejection or `maxTurns`);
- a **playbook candidate** when there is enough evidence of a successful sequence.

Infrastructure failures are classified by an enumerated `errorClass` — transport/timeout, 429,
5xx, auth/key, gateway/budget, configuration, sandbox/tool or cancellation — and do **not** create
a lesson proposal. The agent throws `AgentFailure` with that class; the generated wrapper checks the
class, never the exception text. `task_max_turns` is a task failure, not infrastructure. The
proposal text is normalized before deduplication: UUIDs, timestamps and long numbers become
placeholders, so two identical failures with different IDs produce a single proposal.

### Artifact validation

When a vertex declares `validationRules` — a path with `{itemId}`, a minimum size and a content
pattern — the runtime evaluates the rules **after** the agent finishes without an exception. The
verdict is stored in `memory_validation`, linked to the vertex episode, with
`validator_id=artifact-rules`, the SHA-256 of the canonical rules and the hash of the artifacts
read. Infrastructure or task failures produce no verdict: the episode stays **without a verdict**.

With `globalDefaults.memory.validatedReinforcement` enabled, the agent result no longer changes
utility; only the verdict reinforces the items used in that run. Disabled (the default), the 2.5.0
behavior is preserved. The playbook gate always uses the verdict, with or without the switch.

Proposals stay pending in the **Project Memory** panel. Approval promotes the item to active
knowledge; rejection keeps the record for audit. There is no direct lesson-writing tool.

Every promotion and demotion writes an **evidence snapshot** to `memory_evidence` in the
knowledge database: target, action, source episode (when available), validator, artifact hash,
summary and excerpt hash. The snapshot has **no foreign key to the episode**, so telemetry
retention can delete old episodes, hits and validations without deleting the proof. The report and
the panel show how many snapshots exist and how many active items lack evidence.

Playbooks leave `candidate` only with independent validation. The gate requires **3 distinct
`input_hash` values** among the last 20 validated runs for the same `task_type`, a stable validator
and at most **1 promotion per `task_type` in 24h**. Two consecutive failures or more than 30%
failures in 10 validated runs return the playbook to candidate. In the panel, an active playbook has
a **Back to candidate** button; the CLI equivalent is `memory unpromote`.

Facts also have **predicate cardinality**. Accumulation predicates — `USES`, `USES_TOOL`,
`PRODUCES`, `READS`, `WRITES`, `TOUCHES`, `CITES`, `INCLUDES`, `TAGGED_WITH`, `HAS`, `DEPENDS_ON` —
accept multiple active objects. Functional and unknown predicates are single-valued: promoting a
new value ends the previous one (`superseded`, with history) instead of leaving two active values.
The contradiction detector ignores multi-valued predicates.

## 6. Agent tools

| Tool | Effect |
| :--- | :--- |
| `memory_search` | Read-only search over project knowledge and authorized workspace knowledge. |
| `memory_propose_lesson` | Records a pending lesson proposal; does not activate knowledge. |
| `memory_state_get` | Reads a declared state key; the value is labeled untrusted. |
| `memory_state_set` | Writes with CAS (`expected_version`); `learn` mode only. |
| `memory_state_list` | Lists visible keys and metadata, without values. |
| `memory_state_history` | Lists versions of a `versioned` key. |

`memory_record_lesson`, `memoryWriteKeys` and the native `arestrix.memoria` server were removed.
Knowledge is accessed by the runtime and the panel, not by a parallel key-value store.

## 7. Search and embeddings

Search combines:

- **lexical** (FTS), always available;
- optional **vector** search when an embedding provider is configured;
- **RRF fusion** to rank both result sets.

Search **does not index** during a query. Indexing happens outside the read path: at the end of
every persistent run (default budget of **10 s or 64 objects**), in the maintenance worker
(`idle`/`after_episodes`) and in the panel's explicit **Test** and **Reindex** actions. An embedding
provider failure never fails the run. Ready profiles:

| Profile | Stored dimensions | Note |
| :--- | :--- | :--- |
| EmbeddingGemma 2 | 768 | full vector; also accepts 512, 256 and 128 via MRL |
| Qwen3-Embedding-4B | 768 | truncated from 2560; accepts 32 to 2560 via MRL |

Without a provider, search keeps working in lexical mode.

Each model has its own representation prefix. **Qwen3** receives the query instruction
`Instruct: Given a task description, retrieve memory items that help complete it` followed by
`Query:`; the document gets no prefix. **EmbeddingGemma 2** uses distinct query and document
prefixes. The instruction text is versioned and part of the **fingerprint**: changing it
invalidates the index.

The **model revision** field (`embeddingRevision`) records the server digest/revision when
provided; it is also part of the fingerprint. **MRL truncation** (`embeddingTruncateDim`, 0 = full)
reduces the vector and **renormalizes it to norm 1**; NaN/Inf or zero-norm vectors are rejected.
Accepted dimensions: EmbeddingGemma 2 at 768, 512, 256 or 128; Qwen3 from 32 to 2560.

The index stores a SHA-256 **fingerprint** of the endpoint, model, revision, effective dimension,
truncation, prefixes/instruction, normalization, metric and index version. Search only uses vectors
from the current fingerprint and never mixes old indexes. Changing the model, revision, dimension,
truncation or instruction leaves the index `stale` and requires reindexing. Status shows the model,
dimensions, revision, indexed items, candidates, pending items and a short fingerprint, with these
states:

| State | Meaning | Search |
| :--- | :--- | :--- |
| `ready` | Current fingerprint, complete index | hybrid |
| `stale` | Model/dimension/endpoint/template changed | lexical |
| `pending` | Reindex in progress | lexical |
| `partial` | Incomplete index | hybrid: vector for indexed items, lexical for the rest |
| `failed` | Reindex failed | lexical + error |

In `partial`, items with a vector enter the lexical + vector fusion; items still without a vector
enter only through the lexical side, without turning hybrid search off. `memory health` and the
panel show indexed and pending totals.

Changing profiles invalidates the index and offers reindexing. Reindexing is idempotent and
discards vectors from old fingerprints.

## 8. A/B measurement

The panel offers **Preview brief size**. The action:

1. creates a consistent copy of knowledge with `VACUUM INTO`;
2. computes the SHA-256 fingerprint of the copy;
3. measures, per active vertex, brief tokens and characters, lessons, facts and playbooks;
4. compares with the no-memory baseline (zero).

This is **A/B v1**: it measures context cost and content, not the validator approval rate. The full
executor is the `memory ab run` command described below.

**A/B v2** is the full statistical protocol. The versioned suite
[`tests/fixtures/memory-ab-v1.json`](../../tests/fixtures/memory-ab-v1.json) has 20 tasks — 12 with
relevant knowledge, 4 controls and 4 known failures — and each declares its `input_hash`. The CLI
validates the suite, shuffles an interleaved order with a seed and analyzes observations:

```bash
arestrix-cli memory ab validate --suite tests/fixtures/memory-ab-v1.json
arestrix-cli memory ab order --suite tests/fixtures/memory-ab-v1.json \
  --repetitions 3 --seed 42 --json
arestrix-cli memory ab run --suite tests/fixtures/memory-ab-v1.json \
  --pipeline pipeline.json --node gerador --repetitions 3 --seed 42 --json
```

`memory ab run` actually executes the pilot. It freezes knowledge with `VACUUM INTO` and opens that
copy read-only (`SQLITE_OPEN_READONLY` and `PRAGMA query_only`) in the ON arm; the OFF arm sets
`ARESTRIX_MEMORY_DISABLE=1`. Both halves write telemetry to the same measurement database, with
`ab_arm` and `ab_repetition` on every row. Infrastructure failures are retried up to twice and
counted outside the verdict; tasks without a validator appear in `invalidTasks` and do not enter the
pair.

The primary metric is **validator approval**, compared in pairs. The report includes paired deltas,
95% CI (Student t), tokens, turns, cost and latency, plus the knowledge fingerprint before and after
the measurement. `memory ab report` remains available for analysing an observation file collected
elsewhere.

### Recurrence milestone

E10 measures whether tasks repeat often enough to justify paths. The episode
records `intent_template_hash`, the SHA-256 of the vertex `promptTemplate`
before variable substitution. The template is configuration, not the user
prompt, so this field never stores input text.

```bash
arestrix-cli memory report --recurrence --json
arestrix-cli memory report --recurrence --since 2026-10-01T00:00:00Z \
  --min-verdict-rate 0.70 --min-citation-rate 0.30 \
  --min-executions 5 --min-distinct-inputs 3 --min-reuse-rate 0.20
```

For each `task_type`, the report includes executions, executions with a verdict,
approval rate, distinct `input_hash` values, (`task_type`,
`intent_template_hash`) pairs, citation rate, reuse rate and tokens per
execution. Reuse is the fraction of executions that cite an item already cited
by an earlier execution of the same `task_type`. The result selects one of
`continue_full`, `continue_base_knowledge` (E11–E14, paths deferred),
`fix_validators` or `insufficient_data`. The thresholds used are stored in the
JSON.

### Local sources and passages

With `globalDefaults.memory.sources` enabled, memory ingests text, Markdown and
code files **after** execution, without calling a language model:

- files successfully read by the `read` tool;
- folders or files declared in `memory.sources.paths`.

Ingestion applies an extension allowlist, `maxFileBytes` (default 512 KiB),
`maxFiles` (default 2,000) per run, fixed exclusions (`.git`, `node_modules`, `.arestrix`,
`.workspace/memory`) and secret sanitization. Content is segmented
deterministically: Markdown by headings/paragraphs, code by top-level blocks and
text in 1,000-character windows with 200 characters of overlap.

Each source version has a `content_hash`; changes create a new version and old
passages become `superseded`, preserved as evidence. Re-ingesting identical
content is a no-op. `memory_search` returns passages with `[MEMO:psg:<id>]`,
path and position; citing the ID marks the passage as used. The brief does not
include passages at this stage.

### Retrieval traces

Every knowledge write bumps `knowledge_version` in the same transaction; reads
and telemetry do not. Every memory-enabled vertex execution records a
`memory_trace` with the version consulted, the brief and searches, candidates
with lexical/vector/fused scores, position and delivered status, plus the items
actually used. The trace closes with the episode and is idempotent by
`(run_id, node_id)`.

```bash
arestrix-cli memory trace show <run> <node> --project . --json
```

Each query stores at most 50 candidates and each execution at most 8 steps; the
overflow is counted in `truncatedCandidates`/`truncatedSteps`. The query itself
is stored as a hash, not as text.

### Cost per run

Telemetry records prompt, output and **prompt cache** tokens: cache reads (`cached_tokens`) and cache
writes (`cache_write_tokens`) when the provider reports them. The panel and
`arestrix-cli memory report` show the totals; effective cost uses the provider's normal, cached and
cache-write prices.

## 9. Retention, security and scope

- **Strict scope:** project knowledge does not leak into another project; the workspace is read only
  when configured and authorized.
- **Sanitization:** known secrets are removed before any write, legacy read or export.
- **Retention:** affects telemetry (episodes, hits, usage). Knowledge is not deleted by the retention
  routine.
- **Session clearing:** in ephemeral memory, clears only the session; it never purges a file database.
- **Audit:** approvals, rejections, promotions, conflicts and purges leave a trail.

## 10. Continuation state

Continuation state replaces the old Blackboard and `arestrix.memoria`. It stays **outside the
brief** and is reachable only through tools.

- The key is **declared by the project**; the agent never creates a key.
- Identity: `(scope_kind, scope_owner, key)`.
- Scopes: `project`, `task_type` and `item`. Each key has a single scope, with no merge between them.
- The value is validated against a JSON Schema subset **after** secret sanitization.
- `replace` keeps only the current version; `versioned` keeps the last K versions.
- TTL is applied on read.
- CAS: absent `expected_version` creates; equal version writes; a different version returns a
  conflict with the current version and does not overwrite.
- A schema change marks the old value `stale`; the next write provides the current version.
- `memory_state_list` does not return values. Reads are labeled as untrusted data from a previous
  run.
- Writes, refusals and conflicts are audited; reads are not.

In the Studio, the **State** tab in the **Project Memory** panel lists declared keys and lets you
create one with scope, schema, TTL, mode and retained versions. The agent still cannot create keys.

Declare and operate manually through the CLI:

```bash
arestrix-cli memory state declare --project . --key cursor --scope project \
  --schema '{"type":"object","properties":{"n":{"type":"integer"}},"required":["n"]}'
arestrix-cli memory state set --project . --key cursor --value '{"n":1}'
arestrix-cli memory state get --project . --key cursor --json
arestrix-cli memory state list --project . --json
```

## 11. Quick reference

```text
Project
  .arestrix/memory/memory.db       knowledge
  .arestrix/telemetry/telemetry.db telemetry
  .workspace/memory/memory.db      workspace (optional)

Vertex
  off      does not use memory
  consult  reads the brief and records hits
  learn    reads, records an episode and proposes lessons

Cycle
  execute -> episode -> proposal -> approval -> active knowledge -> brief

Continuation state
  declared key -> memory_state_get/set/list/history -> outside the brief
```

For command-line operations, see [`arestrix-cli.md`](arestrix-cli.md). For the product view and
current limits, see [`workspaces-memory-skills-mcp.md`](workspaces-memory-skills-mcp.md).

## 12. Institution

The `arestrix-memory` service exposes institution knowledge over authenticated HTTP and MCP (stdio
and `/mcp`), with tokens, `viewer`/`editor`/`admin` roles and invariant scope. It is optional and
separate from the project's private database.

## 13. Deployment status

The operational memory deployment is complete: modes, proposals, validation, continuation state,
telemetry, fingerprinted embeddings, gated playbooks, A/B v2 and the Studio assistant tools.

The simplification plan (Phases A-C) is complete. Phase D — the advanced multigraph with facets,
domain knowledge, paths over claims and model routing — is a separate program outside this plan and
does not block the release. Embedding retrieval is already implemented.

The institutional level in the assistant and validation with real providers are operational pending
items. The A/B harness is implemented in `memory ab run` and runs with the simulated provider in the
e2e. See [`pending.md`](pending.md).
